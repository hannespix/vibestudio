Hannes Pix Eigene Projekte im LVM
Unsere These: LLM plus Git macht aus einer Chatsitzung ein weiterentwickelbares Projekt. Für eigene Anwendungen in der Verwaltung braucht es danach einen Ort, an dem sie verlässlich laufen und auf freigegebene Daten zugreifen können. Diese Präsentation führt zum Vorschlag einer internen GitLab-Umgebung und – noch dringender – einer Container- und Datenbankumgebung im LVM. Das ist ein Zielbild, keine Aussage über bereits vorhandene Infrastruktur. Sechs kurze Kapitelpaare, etwa sieben Minuten. Alle Naturmotive sind KI-generierte, dekorative Bilder.

festhalten

das wichtige bleibt im projekt

Ein langer Chat ist kein belastbarer Projektstand. Bei wachsendem Kontext muss ein Agent Informationen verdichten oder neu einlesen. Das ist nützlich, aber die Zusammenfassung kann Details verlieren. Deshalb sichern wir nicht nur Code, sondern auch Ziele, Entscheidungen und nächste Schritte außerhalb der Sitzung.

Git vergrößert kein Kontextfenster. Wissen muss als Datei festgehalten und erneut gelesen werden.

Claude Code verdichtet den Gesprächsverlauf bei wachsendem Kontext; frühe Detailanweisungen können dabei verloren gehen. Auch ein Agent mit Git hat weiterhin ein begrenztes Kontextfenster. Der Vorteil liegt außerhalb davon: versionierte Dateien und eine nachvollziehbare Historie. Unsere Arbeitsweise: Ziel und Startanleitung in README, wichtige Entscheidungen und offene Aufgaben in kurzen Projektnotizen festhalten und gemeinsam mit dem Code committen. Ein neuer Agent muss die relevanten Dateien aktiv lesen; der gesamte alte Chat wird nicht automatisch übertragen. Je nach Werkzeug ergänzen CLAUDE.md oder AGENTS.md die Anweisungen. Die Dateien müssen aktuell gehalten werden. Quellen: https://code.claude.com/docs/en/how-claude-code-works ; https://code.claude.com/docs/en/memory ; https://opencode.ai/docs/rules/ . frei bleiben

das projekt gehört in unsere hand

Ein Projekt in Git kann mit unterschiedlichen Werkzeugen weiterbearbeitet werden. Das macht die Wahl des Agenten und – innerhalb seiner Möglichkeiten – des Sprachmodells flexibler. Wir sollten daher die Projektdateien und die Betriebsumgebung zum dauerhaften Fundament machen, nicht eine einzelne Chatsitzung.

Ziel: internes GitLab

Neuer Agent liest den Stand. Wir arbeiten weiter.

Modellwahl und automatische Anweisungsdateien hängen vom jeweiligen Werkzeug ab.

Harness bezeichnet hier die Arbeitsumgebung, die das Modell mit Dateien und Werkzeugen verbindet. Die Git-Dateien sind unabhängig davon bearbeitbar. Claude Code verwendet Claude-Modelle; OpenCode unterstützt mehrere Anbieter und auch lokale Modelle. Freie Wahl bedeutet deshalb nicht, dass jedes Modell in jedem Harness funktioniert. Zugänge, Integrationen, Freigaben und spezielle Anweisungsdateien müssen zum Werkzeug passen. Unser Übergabeprinzip: Änderungen sichern, Stand und nächste Schritte dokumentieren, neues Werkzeug auf dasselbe Repository zugreifen und relevante Dateien lesen lassen. Git überträgt weder die vollständige Sitzung noch automatisch Plattformfunktionen wie Issues und Berechtigungen. Die organisatorische Folgerung ist unser Vorschlag: ein internes GitLab als gemeinsamer Projektort. Quellen: https://code.claude.com/docs/en/how-claude-code-works ; https://opencode.ai/docs/providers/ ; https://opencode.ai/docs/rules/ ; https://docs.gitlab.com/user/project/ . Stand: 25.09.2026.

betreiben

eigene anwendungen. interne daten.

Ein Repository allein betreibt keine Anwendung. Für eigene Fachwerkzeuge brauchen wir eine verlässlich betreute Laufzeitumgebung und eine Datenbank. Die folgende Darstellung ist unser Vorschlag für den Zielbetrieb im LVM, keine bestätigte Architektur.

Interne Datenhaltung bedeutet nicht automatisch interne KI-Verarbeitung.

Vorgeschlagen ist eine intern betriebene Umgebung für eigene Anwendungen: GitLab für Code und Projektdokumentation, eine Container-Laufzeit für die Anwendung und ein betreuter Datenbankdienst für persistente Daten. Die konkrete Plattform und Datenbank wählt der Betrieb passend zu vorhandenen Standards. Der Datenbankdienst muss nicht selbst im selben Container laufen. Für einen Pilot braucht es geklärte Identitäten und Rechte, getrennte Test- und Produktionsumgebungen, geschützte Zugangsdaten, persistente Speicherung, Backups mit Wiederherstellbarkeit sowie Zuständigkeit für Updates und Überwachung. Container allein sind keine Freigabe für Produktivdaten. Entwicklung zunächst mit synthetischen oder freigegebenen Testdaten; Produktivdaten nur im genehmigten Betrieb und mit erforderlichen Rechten. Ein externer LLM-Dienst kann trotz internem GitLab oder lokalem Agenten über Prompts, Dateiinhalte oder Logs Daten erhalten. Deshalb Modellendpunkt und erlaubte Datenflüsse ausdrücklich freigeben und technisch begrenzen. Weder Git noch ein Code-Rollback ersetzt Datenbank-Backups oder eine Migrationsstrategie. Dieses Zielbild ist ein Vorschlag für die Abstimmung mit dem zuständigen Betrieb, keine geprüfte LVM-Sicherheitsarchitektur.

Die dringendere Lücke ist die Laufzeit mit Datenbank – sonst bleibt auch guter Code ein Prototyp. Start: ein Pilotprojekt mit klarer Betriebsverantwortung.

Mein Vorschlag für die Verwaltung: Ein gemeinsames internes GitLab für eigene Projekte bereitstellen und mit höherer Dringlichkeit eine betreute Container- und Datenbankumgebung ermöglichen. Ein Pilot sollte an einem konkreten internen Bedarf starten, mit Fachverantwortung, Betriebsverantwortung und einer klar abgegrenzten Datenfreigabe. Zuerst mit Beispieldaten nachweisen, dass Funktion, Bereitstellung und Wiederherstellung funktionieren; danach den Einsatz mit freigegebenen Produktivdaten ermöglichen. Das Ziel ist ein tatsächlich nutzbares und weiterentwickelbares Werkzeug. LLM plus Git erleichtert die Entwicklung und Übergabe. Die interne Plattform macht daraus einen nachhaltigen Betrieb. Zuständigkeiten, Ressourcen und technische Standards sind noch zu vereinbaren; diese Folie behauptet keine bereits erteilte Freigabe.
