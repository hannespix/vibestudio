Das Sprachmodell entwirft und schreibt. Der Agent, oft Harness genannt, verbindet es mit Dateien, Terminal und Werkzeugen: Er liest das Projekt, ändert Dateien, führt Tests aus. Claude Code ist unser Beispiel; Codex CLI und OpenCode arbeiten nach demselben Prinzip. Der Unterschied

Zeile für Zeile: was neu ist, was weg ist.

pull request

Der Vorschlag

prüfen, besprechen, zusammenführen.

remote

Die gemeinsame Kopie

auf GitHub, GitLab oder dem eigenen Server.

Jeder Stand bleibt erreichbar. Geprüft wird, bevor etwas zählt.

Git ist ein Ordner, der sich an jeden gespeicherten Stand erinnert. Ein Commit ist ein Schnappschuss aller Dateien mit einer kurzen Nachricht; Commits sind billig, man macht viele davon. Ein Branch ist ein Abzweig: Dort probiert man etwas aus, während main stabil bleibt. Der Diff zeigt exakt, was sich geändert hat, deshalb kann man die Arbeit eines Agenten überhaupt prüfen. Ein Pull Request (bei GitLab Merge Request) ist der Vorschlag, einen Branch zusammenzuführen: Er bündelt Diff, Gespräch und automatische Prüfungen; wer freigibt, entscheidet. Der Remote ist die gemeinsame Kopie auf einer Plattform; jeder im Team holt sie sich und schickt Änderungen dorthin. Der Graph unten erzählt genau das: Commits auf main, ein Branch zweigt ab, wird geprüft und kommt zurück. Quellen: https://git-scm.com/book/de/v2 ; https://docs.github.com/en/pull-requests . Ein Auftrag, eine Sache.

Notizen nach jeder Runde.

Reviews ernst nehmen. Immer.

Der Agent liefert Vorschläge. Das Repo hält, was wir freigeben.

Agentisches Coding funktioniert dann gut, wenn die Schleife klein bleibt. Auftrag: ein Ziel, ein Rahmen, ein Kriterium, woran man Erfolg erkennt. Kontext: Der Agent liest README, Notizen und Anweisungsdatei, bevor er anfängt; was dort nicht steht, weiß er nicht. Änderung: immer auf einem Branch, mit Tests oder zumindest einer Prüfung, die er selbst ausführen kann. Prüfung: Wir lesen den Diff und probieren es aus; konkrete Rückmeldung schlägt allgemeine Kritik. Merge: Erst dann ist es Teil des Projekts. Die Regeln rechts sind Erfahrungswerte: Ein Auftrag pro Runde, Tests als Sicherheitsnetz, dauerhafte Regeln in CLAUDE.md oder AGENTS.md, Notizen nach jeder Runde, Reviews nie überspringen. Der Kreis unten läuft beliebig oft; jede Runde hinterlässt einen Commit. Quellen: https://code.claude.com/docs/en/best-practices ; https://agents.md . Stand: 27.09.2026.

vom prototyp ins projekt

Ein Repository allein betreibt nichts. Für Werkzeuge im Raum, ob Steuerung, Anzeige oder Auswertung, braucht es einen Ort, an dem der Code läuft, und einen nachvollziehbaren Weg vom Commit dorthin.

Im Raum

Test und Produktion trennen. Was im Raum läuft, hat einen Commit.

Auch Medienserver, kleine Rechner und Displays lassen sich aus dem Repo versorgen.

Vom Repo führt ein automatischer Schritt in den Betrieb: Ein Merge auf main baut die Anwendung und stellt sie bereit, als Container, als statische Seite (etwa GitHub Pages, wie diese Präsentation) oder als Paket auf einem kleinen Rechner im Raum. Die Anwendung spricht mit Geräten und Daten: Sensoren, Displays, Medienserver, Datenbanken. Zwei Regeln halten das stabil: Test und Produktion trennen, damit Versuche nichts im Raum stören; und jede laufende Version einem Commit zuordnen können, damit man weiß, was gerade läuft und zurückgehen kann. Zugangsdaten gehören nicht ins Repo, sondern in die Umgebung. Quellen: https://docs.github.com/en/actions ; https://docs.github.com/en/pages . Stand: 27.09.2026.

Vorschlag für den Einstieg: ein Pilot in zwei Wochen, klein und echt, für etwas, das im Studioalltag fehlt: ein Kalkulationshelfer, eine Statusanzeige für eine Installation, ein Werkzeug zur Medienprüfung. Der Ablauf bleibt derselbe: Auftrag, Branch, Review, Merge, nächste Runde. Nach dem Pilot lässt sich beurteilen, welche Werkzeuge sich lohnen und wie viel Betreuung sie brauchen.
